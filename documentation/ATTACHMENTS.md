# AI-generated attachments — 1.2.0

## Using the feature

Open an issue → Edit with AI. In Answers, additional facts or instructions, enter for example:

> Attach a proposed solution diagram showing the primary and secondary paths. Keep unconfirmed details marked as proposals.

Click Revise with AI. The revised draft can contain a Proposed attachments section with a diagram preview, text preview and Download links. Nothing is added to the ticket by previewing or downloading. Click Apply enhanced ticket to save the textual edits and attachments together. Ask for revisions/removal in the same conversation before applying. The same draft cannot be applied twice.

The first generated draft can also propose files if the user has explicitly requested them in the interaction. Automatic Enhance with AI does not attach files; a model returning files in automatic mode is rejected without applying the result. Existing drafts without attachment fields remain usable.

## Formats and limits

- SVG diagrams are rendered by Ruby from validated node/edge specifications. Arbitrary model-written SVG, HTML, remote images, binary data and executable attachments are not accepted.
- Text files: Markdown, TXT, CSV, JSON, SQL and Mermaid source (.mmd). These are reviewable text proposals; the plugin never executes or imports their contents.
- At most three files per draft; 40,000 bytes per text file and 80,000 text bytes total. Diagrams support 1–18 nodes, at most 36 edges, short labels and cycles. The renderer is intended for small solution/flow diagrams rather than full UML/network-layout tooling.
- Redmine's existing file-size/extension policy also applies at Apply. No new production gems, Graphviz, image-generation service or external converter is needed.
- API output-token/time limits are shared with the ticket draft. Request smaller files if the model cannot finish within those limits.

Display names come from the draft. Actual filenames are generated by the plugin, such as ai-diagram-4-1.svg or ai-document-4-2.md; AI text cannot choose a server path or storage filename. This also keeps model-generated names out of Redmine's native attachment-file logs.

## Privacy, authorization and lifecycle

Draft specifications/text remain in the existing encrypted enhancement payload. Preview/download requires the session owner, current issue visibility/edit/AI access, and draft/applied state. SVG previews use a fixed renderer with escaped labels, no active elements/external resources, a sandbox CSP and nosniff. Text downloads are forced attachments; text previews are HTML-escaped.

Apply rechecks the baseline and permissions under the existing issue/session locks. The attachment service checks Redmine's attachments_addable? permission, validates native Attachment objects before writing, and adds them through the issue's attachment association while its journal is active. All database changes occur inside the existing Apply transaction. Native Attachment callbacks write the files and remove newly created files on rollback; no separate save_attachments staging list is used. No source/database script is executed.

After Apply, files are ordinary Redmine issue attachments with the requesting user as author and normal ticket visibility. Their IDs are retained in the enhancement payload. Purging old AI sessions does not delete these attached ticket files. Use normal Redmine attachment controls to manage them.

Citations in attachment names, text, diagram titles/nodes/edges are checked together with citations in the ticket draft. Unknown evidence IDs reject the result. The AI is instructed to label diagrams as proposals and preserve unknowns. A generated diagram is not proof of the deployed topology.

## Verification and tools

Ruby tests cover artifact limits, graph validation, XML escaping, cycles, citation checks, private download/preview, invalid indices/states, denied permissions, automatic-mode rejection, duplicate Apply, legacy drafts and transaction rollback on issue validation failure. The local harness uses real Rails/SQLite persistence with small Redmine attachment-interface doubles; native file lifecycle behavior is based on inspection of the installed Redmine 7.0.2 source.

test/fixtures/diagram.json is a reusable synthetic DNS-failover example. Tests generate tmp/proposed-dns-failover.svg. For visual QA, run node tools/render_diagram_preview.cjs with an optional absolute Sharp module path; it creates tmp/proposed-dns-failover.png. Sharp is development-only and not packaged or installed on Redmine.

tools/deployment/verify_artifacts.rb takes the fixture path and performs native Attachment validation plus synthetic view/route rendering in a read-only transaction. It does not save an attachment, modify a ticket or call OpenAI. Full live generation, disk writes and notifications should be accepted through a reviewed interactive ticket rather than a deployment-time paid probe.
